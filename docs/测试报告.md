## 4. 缺陷记录

开发与自测阶段发现并修复的问题。保留记录用于说明系统的验证过程。

| 编号 | 缺陷 | 影响 | 定位与修复 |
| --- | --- | --- | --- |
| D-01 | 工作流引擎的终点节点未被执行 | 所有工作流在终点节点直接结束，最后一步（格式化输出）不执行，返回空回答 | `set_finish_point` 原实现把节点名当作终止条件，循环条件 `current != finish` 导致该节点被跳过。改为把终点节点映射到 `END` 标记，节点执行完再终止 |
| D-02 | 导出文件保存路径与返回路径不一致 | `wb.save(path)` 保存到无后缀文件，返回带 `.xlsx` 的路径，下载必然 404 | `export_table` 与 `export_stats_workbook` 中先 `with_suffix` 再保存 |
| D-03 | 聚合统计使用 `func.case` | `func.case` 不是 SQLAlchemy 2.0 的公开 API，`func.sum(case(...))` 才是正确写法，运行时报错 | 改为 `from sqlalchemy import case` 并使用 `func.sum(case((cond, 1), else_=0))` |
| D-04 | 子查询用 `subquery().select()` | SQLAlchemy 2.0 已移除该用法 | 改为 `select(sub.c.team_id)` |
| D-05 | `on_event("startup")` 已弃用 | 新版 FastAPI 可能移除，启动钩子失效导致未建表 | 改为 `lifespan` 上下文管理器 |
| D-06 | 统计查询挂 `joinedload` 后叠加 `count`/`group_by` | 预加载产生多余 JOIN，计数可能重复 | `base_query` 移除 eager-load，仅明细查询按需加载 |
| D-07 | 竞赛推荐逐赛事查询战绩 | 15 个赛事产生 30+ 次 SQL，页面卡顿 | 改为一次 `group_by` 预聚合 + 一次取最近届次，循环内查字典 |
| D-08 | 问答节点重复调用检索 | 同一查询执行两次混合检索 | 删除多余的 `call_tool` 调用，保留一次 |
| D-09 | 文档正文中的 ASCII 双引号导致语法错误 | `make_knowledge.py` 无法导入，知识库文档无法生成 | 统一改为中文引号 `“”` |
| D-10 | 前端基础组件只注册在根实例上 | 子视图解析 `<chart>` / `<stat>` / `<icon>` 时当成未知标签，统计页两个图全空、指标卡变成 `<stat label="…" value="408">` 空壳，页面"结构在、内容没了" | 改为 `app.component(...)` 全局注册，子视图才能取到 |
| D-11 | 备赛排期在赛季已结束时出现负天数 | 输出"2026-11-15 → 2026-06-09 共 -158 天"，阶段全部挤在截止日之后，计划不可用 | 新增 `_pick_deadline` 只选未来节点；`_split_days` 按权重拆整数天；有截止日时先裁剪总窗口 |
| D-12 | 统计维度识别错误 | 词表含"赛项"，而"参赛**项**目"里正好含这个子串，随便问点什么都被按赛事分组；"2025年各赛事"被"年"抢先 | 词表去掉"赛项"；改为按命中词长度选最具体的维度；已作为过滤条件的维度不再拿来分组 |
| D-13 | 出现"获奖"二字就自动加 `awarded_only` | 问"各学院获奖数量"时基数被裁成获奖项目，于是"参赛 174 / 获奖 174 / 获奖率 100%"，等于用自己算自己 | 仅显式说"只看/仅…获奖"才过滤；命中该条件时在回答里加注说明获奖率不具参考性 |
| D-14 | 预算入参别名不识别 | 传 `team_size=5`、`location=省外` 时人数被默认值覆盖成 3 人，总额少算一半；预算说明里写了"报名费"但明细没有该科目 | `normalize_payload` 统一别名（people/team_size/size、distance/location/scope 等）；预算说明改为按实际明细科目生成 |
| D-15 | 报销入参字段名不兼容 | 前端传 `date` / `item`，校验只认 `invoice_date` / `name`，票据齐全仍被判"缺少开票日期" | `_norm_reimb_item` 做别名归一；餐饮类关键词同时扫科目名 |
| D-16 | 样例数据只到当年赛季 | 交付后打开系统，所有赛事都显示"报名已截止"，推荐结果无区分、备赛计划无截止日可倒排；学生出现"大五" | 增加"下一届"赛季（报名窗口落在今天之后）；年级限定在读；`--force` 改按外键倒序删除；预算单号改自增去重 |
| D-17 | 推荐评分撞封顶 | 6 条推荐里 5 条并列 95 分，"按匹配度排序"失去意义 | 基准分由 50 降至 30（理论满分 95）；获奖率改为连续计入；截止日按 14/30/60 天分档 |

D-01、D-02、D-10 属于会直接导致功能不可用的缺陷。D-10 尤其隐蔽：接口全部返回 200、数据也正确，
只有真正用浏览器打开页面才会发现图表是空的——它是在逐页截图核对时被发现的。

D-11 至 D-17 是"能跑出结果、但结果是错的"这一类，共同点是：单看某个函数没问题，
放到真实数据和真实日期下才暴露。它们现在都有对应的回归用例（见第 2.6、2.7 节与第 3 节）。

| 场景 | 期望 | 实现 |
| --- | --- | --- |
| 问题为空 | 400 | `AskPayload` 的 `min_length=1` |
| 会话不存在 | 404 | `db.get` 判空 |
| 上传不支持的文件类型 | 记录到 errors，不中断其他文件 | 逐文件 try/except |
| 赛事不存在 | 400 且提示名称 | `_prep_resolve` 抛 ValueError |
| 统计维度非法 | 400 | `aggregate` 抛 ValueError |
| 下载非法文件名 | 400 | 路径必须在 `OUTPUT_DIR` 内 |
| 工作流执行异常 | 500 并记录到 `agent_run` | `run` 接口 try/except |

## 6. 知识问答准确性测试

### 6.1 测试设计

竞赛政策的问答没有标准答案库，采用"**原文可核验**"作为判定标准，而非简单的字符串匹配。

判定规则：

| 等级 | 判定 |
| --- | --- |
| 通过 | 回答要点能在引用的片段原文中逐字找到，且数字/日期完全一致 |
| 部分通过 | 结论正确但引用不全，或表述有出入但事实无误 |
| 不通过 | 出现片段中没有的内容；数字/日期错误；引用指向无关片段 |

### 6.2 测试集

### 6.4 当前状态说明

**已执行的部分（未接入大模型，抽取式回答模式）**：

| 类别 | 题数 | 结果 |
| --- | --- | --- |
| 可答问题（报名时间、住宿标准、报销材料等） | 3 | 3/3 给出结论，均带 4-6 条原文引用，关键数字与原文一致 |
| 无据问题（不存在的赛事、院长手机号、专利申请） | 3 | 3/3 明确拒答（`mode=no_hit`），未编造内容 |

拒答判断不依赖模型，而是两道确定性闸门：检索得分低于阈值、或问题的核心词在命中片段中覆盖率不足，
都直接返回"知识库中未收录"，而不是硬凑一段相似文字。实测可答题的覆盖率 ≥0.62，无据题 ≤0.55，
两者之间留出了可调的安全间隔。

**尚未执行的部分**：配置大模型后的 30 题逐题走查。原因：

- 不同模型对同一 Prompt 的遵循度不同，更换模型后结论会变；
- 学校真实文档的排版、切块质量与样例文档不同；
- 逐题判分需要人工核对原文，无法自动化。

本报告不预先填写未经执行的准确率数据。建议在正式交付演示前，用第 6.2 节的题集走查一遍并填入 6.3 节表格。

## 7. 性能基线

实测环境：Windows 11 / Python 3.13 / SQLite(WAL)，数据规模 408 个项目、6 份文档 25 个片段，未接入大模型。

| 操作 | 实测耗时 | 说明 |
| --- | --- | --- |
| 全量初始化（建表 + 造数 + 导知识库） | 2.8 s | `python scripts/init_all.py` 一次跑完 |
| 知识库导入 | 6 份文档约 1.5 s | 含切块与本地向量 |
| 8 条工作流平均 | **6 ms** | 17 次调用统计，含数据库查询 |
| 数据统计（含 join + group_by） | 15-21 ms | 最慢的一条 |
| 备赛规划 | 10-11 ms | 含 4 路检索 |
| 知识问答（无模型） | 4-10 ms | 检索 + 抽取式组织 |
| 知识问答（接入 DeepSeek 后） | 2-6 s | 主要为模型响应时间，取决于网络 |
| 统计 Excel 导出 | 约 0.2 s / 33 KB | openpyxl |
| Word 单据导出 | 约 0.2 s / 37-38 KB | python-docx |
| 首屏渲染 | < 1 s | Vue/ECharts 均为本地静态文件，无外网依赖 |

检索为纯 Python 实现（BM25 + 哈希向量），未引入向量数据库，因此整套系统可以直接拷贝到内网机器上运行。
按当前索引结构，片段数在 5000 以内时单次检索可控制在 100 ms 内；超过此规模建议引入向量库或缩小 top_k。

真正把它们找出来的是"用真实数据跑一遍完整链路"和"用浏览器打开页面看一眼"，
而不是只看函数是否返回、状态码是否为 200。

系统在未配置大模型时可完整运行（规则引擎 + 抽取式回答 + 拒绝编造），
可作为对照基线，便于评估接入大模型后带来的实际增益。
业务层已全部验证；问答层的逐题准确率需在现场按第 6.2 节题集执行并记录。
