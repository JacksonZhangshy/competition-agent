# 数据库设计说明

数据库：默认 SQLite 3（`data/app.db`），可切换 MySQL 8 / PostgreSQL 14。
ORM：SQLAlchemy 2.0（声明式映射，`DeclarativeBase`）。
建表：由 `backend/database.py::init_db()` 根据模型自动创建，无需手写 DDL。

---

## 1. 实体关系

```
competition 1 ──── n edition 1 ──── n team 1 ──── n team_member n ──── 1 student
                                      │                    │
                                      ├── 1 student（负责人）
                                      ├── 1 teacher（指导教师）
                                      ├── n budget_request ── 1 loan_request
                                      └── n reimbursement

knowledge_doc 1 ──── n knowledge_chunk

conversation 1 ──── n message
agent_run（独立，记录每次工作流执行轨迹）
system_config（键值配置：开支标准、推荐权重）
```

## 2. 表结构

### 2.1 `student` 学生

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | int PK | |
| sno | str(32) unique | 学号 |
| name | str(64) | 姓名 |
| gender | str(8) | 性别 |
| college | str(64) idx | 所属学院（统计"按学院对比"用的维度，由数据导入时维护） |
| major | str(64) idx | 专业 |
| grade | int idx | 入学年份（如 2023） |
| class_name | str(64) | 班级 |
| phone / email | str | 联系方式 |

`grade_label` 为计算属性：按当前年份换算为"大一…大四"。

### 2.2 `teacher` 教师

| 字段 | 类型 | 说明 |
| --- | --- | --- |

| dept | str(64) | 所属单位 |
| phone / email | str | 联系方式 |

### 2.3 `competition` 赛事（跨年度稳定信息）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | int PK | |
| code | str(32) unique | 赛事代码，如 `IEC`、`ACM` |
| name | str(200) | 全称 |
| short_name | str(64) | 简称 |
| level | str(32) idx | 国家级 / 省级 / 校级 / 行业级 |
| category | str(32) idx | 学科竞赛 / 创新创业 / 程序设计 / 数学建模 / 电子设计 / 外语 |
| organizer | str(200) | 主办单位 |
| official_url | str(300) | 官网 |
| majors | str(300) | 适配专业，逗号分隔，空表示不限 |
| grades | str(64) | 适配年级，如 `2,3,4` |
| difficulty | int | 难度 1-5 |
| workload | int | 备赛投入 1-5 |
| description | text | 简介 |
| tags | str(300) | 标签，逗号分隔 |
| is_active | bool | 是否在赛事目录中 |

### 2.4 `edition` 赛事届次（统计主维度）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | int PK | |
| competition_id | FK→competition idx | |
| year | int idx | 年度 |
| seq | int | 第几届 |
| notice_title | str(300) | 通知标题 |
| signup_start / signup_end | date | 报名起止 |
| contest_start / contest_end | date | 比赛起止 |
| fee | float | 报名费（元/队） |
| venue | str(128) | 地点 |
| status | str(16) | 未开始 / 报名中 / 进行中 / 已结束 |
| rules_json | JSON | 报名条件、材料清单、奖项设置、赛程 |

唯一约束：`(competition_id, year)`。

`rules_json` 结构示例：

```json
{
  "eligibility": ["全日制在校本科生", "每人限报 1 项"],
  "materials": ["报名表", "参赛作品说明", "原创性声明", "指导教师推荐意见"],
  "award": ["一等奖 10%", "二等奖 20%", "三等奖 30%"],
  "schedule": ["校级选拔（4 月）", "省级复赛（5-6 月）", "全国决赛（7-8 月）"]
}
```

**为什么把规则放 JSON 而不是拆表**：不同赛事的规则条目差异极大，拆表会产生大量稀疏列；放 JSON 便于整体替换，且新增赛事时只需填一段 JSON，不用改表结构或代码。代价是无法对规则内部字段做 SQL 查询——但业务上不需要。

### 2.5 `team` 参赛项目（统计最小颗粒度）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | int PK | |
| edition_id | FK→edition idx | |
| project_name | str(300) | 项目名称 |
| leader_student_id | FK→student idx | 负责人 |
| teacher_id | FK→teacher idx | 指导教师 |
| status | str(16) idx | 报名 / 备赛 / 参赛 / 获奖 / 未获奖 |
| award_level | str(16) idx | 特等奖 / 一等奖 / 二等奖 / 三等奖 / 优秀奖 / 无 |
| award_grade | str(16) idx | 国家级 / 省级 / 校级 / 无 |
| signup_date / finish_date | date | 报名日 / 完成日 |

| remark | text | 备注 |

`award_level = "无"` 表示未获奖，与"未参赛"通过 `status` 区分。这个约定是全部获奖率计算的基础。

| --- | --- | --- |

| category | str(32) idx | 政策 / 规程 / 通知 / 模板 / 其他 |
| year | int idx | 年份，可空 |
| source_path | str(500) | 原文件路径 |
| char_count | int | 字符数 |

| status | str(16) | 已入库 |

| created_at | datetime | |

### 2.11 `knowledge_chunk` 检索片段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | int PK | |
| doc_id | FK→knowledge_doc idx | |
| seq | int | 文档内序号，用于引用定位 |
| content | text | 片段正文 |
| heading | str(300) | 所属章节 |
| page | int | PDF 页码，可空 |
| char_count | int | |
| vector | JSON | 向量（float 数组） |
| tokens | text | 分词结果，空格分隔，用于 BM25 |

`seq` 与 `doc_id` 组合是引用溯源的关键：前端「查看原文」按 `chunk_id` 取回完整片段，用户可与原始文件逐段比对。

`tokens` 冗余存储是为了避免每次构建索引都重新分词（jieba 分词 60 个片段约 0.3 秒，量大时累积可观）。

### 2.12 `conversation` / `message` 会话

`conversation`：id、title、created_at、updated_at
`message`：id、conversation_id（FK idx）、role（user/assistant）、content、citations（JSON）、meta（JSON）、created_at

`citations` 保存该轮回答的引用快照，即使知识库后续变更，历史记录里的出处仍可追溯。

### 2.13 `agent_run` 执行轨迹

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | int PK | |
| workflow | str(64) idx | 工作流 key |
| status | str(16) | success / error |
| input_data / output_data | JSON | 入参出参 |
| trace | JSON | 节点级轨迹数组 |
| duration_ms | int | 总耗时 |
| created_at | datetime idx | |

`trace` 元素：`{"node","description","status","duration_ms","error"}`。

这张表是《测试报告》和界面「系统状态」的数据来源，也是答辩时展示"Agent 到底做了什么"的证据。

### 2.14 `system_config` 系统配置

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| key | str(64) unique | 配置键 |
| value | JSON | 配置值 |
| remark | str(300) | 说明 |

内置两条：

- `budget_rules`：开支标准。含 `categories`（科目）、`standards`（各科目单位与单价，按本地/省内/省外分档）、`limits`（单队上限、材料费占比）、`required_attachments`（必备附件）。
- `recommend_weights`：推荐打分权重（预留，当前权重在代码中）。

`budget_rules` 完整结构见 `backend/services/budget.py::DEFAULT_RULES`。改标准只改这条记录，不用动代码——这是"避免规则固化在代码中"的落点。

## 3. 索引设计

| 表 | 索引 | 用途 |
| --- | --- | --- |
| student | sno（唯一）、college、major、grade | 学生检索、学院/专业统计 |
| teacher | tno（唯一） | 教师检索 |
| competition | code（唯一）、level、category | 赛事筛选 |
| edition | competition_id、year，唯一(competition_id, year) | 年度统计 |
| team | edition_id、leader_student_id、teacher_id、status、award_level、award_grade | 多维统计 |
| knowledge_doc | category、year | 知识库筛选 |
| knowledge_chunk | doc_id | 片段定位 |
| agent_run | workflow、created_at | 轨迹查询 |

统计查询的典型路径是 `team` join `edition` join `competition`，这三个表的外键均已建索引。

## 4. 统计口径

以下口径在 `backend/services/stats.py` 中固化，界面上不做二次解释：

| 指标 | 口径 |
| --- | --- |
| 参赛项目数 | `team` 表记录数 |
| 获奖数 | `team.award_level != '无'` 的记录数 |
| 获奖率 | 获奖数 ÷ 参赛项目数 × 100，保留一位小数 |
| 国家级获奖 | `award_grade = '国家级'` 且 `award_level != '无'` |
| 经费总额 | `SUM(team.budget_total)` |
| 专业维度 | 按**项目负责人**专业归集 |
| 学院维度 | 按负责人的 `student.college` 归集；该字段为空时归入"未填写" |
| 教师维度 | 按 `team.teacher_id` 归集（一个项目只算给第一指导教师） |
| 学生维度 | 按负责人归集；查某学生全部参赛记录时包含其作为成员的场合 |
| 年度维度 | 按 `edition.year`，不是报名日期所在年 |

**为什么专业按负责人归集**：若按全部成员展开，一个跨专业项目的 3 个人会让参赛数变 3 倍，获奖率失真。按负责人归集保证"项目数"在任何维度下总量一致，可加总校验。这个取舍需要在使用说明中向学院明确，避免与既有报表口径冲突。

## 5. 数据迁移建议

从学院现有 Excel 台账迁移时，建议按以下顺序：

1. `competition`：先按赛事字典录入（去重，一个赛事一条）
2. `edition`：按年度补齐，`rules_json` 可先留空后补
3. `teacher`、`student`：按工号/学号去重
4. `team`：按项目逐条录入，注意 `award_level` 未获奖统一填 `"无"` 而非空值
5. `team_member`：可选，用于学生维度的完整统计

注意：`award_level` 为空字符串会导致获奖数统计出错，导入时务必归一化为 `"无"`。
