# Agent 工作流与 Prompt 配置说明

本文档说明智能体的编排结构、每个节点的职责与输入输出、可调用的工具，以及全部提示词的设计意图。

---

## 1. 分层设计

```
┌─────────────────────────────────────────────────────┐
│  工作流层  backend/agent/workflows.py                │
│  8 张 StateGraph：qa / recommend / prep / review     │
│                   budget / loan / reimburse / stats  │
└───────────────────────┬─────────────────────────────┘
                        │ 节点内调用
┌───────────────────────▼─────────────────────────────┐
│  工具层  backend/agent/tools.py                      │
│  17 个确定性工具：检索、查询、聚合、测算、校验        │
└───────────────────────┬─────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────┐
│  能力层                                              │
│  rag/（检索）  services/（统计·经费·导出）  llm.py    │
└─────────────────────────────────────────────────────┘
```

核心约束：**模型只出现在"组织语言"和"重排序"两类节点**。凡涉及数字、日期、金额、名单、统计口径的处理，全部由工具层完成并作为事实来源。

这样做的理由来自需求原文——"重要竞赛政策和数据不能仅依赖大模型生成；竞赛统计结果应以结构化业务数据为准"。

## 2. 工作流引擎

`backend/agent/graph.py`，约 200 行，无第三方依赖。

### 2.1 接口（与 LangGraph 对齐）

```python
g = StateGraph("知识问答")
g.add_node("retrieve", fn, "知识库混合检索")     # fn(state, ctx) -> dict 增量更新
g.add_edge("analyze", "retrieve")               # 固定边
g.add_conditional_edges("retrieve", router, {"answer": "answer", "no_hit": "no_hit"})
g.set_entry_point("analyze")
g.set_finish_point("answer")                    # 该节点仍会执行，执行完结束
compiled = g.compile(max_steps=30)
state = compiled.invoke({"question": "..."}, ctx)
```

### 2.2 语义

| 概念 | 说明 |
| --- | --- |
| `state` | 普通 dict，节点返回的 dict 合并进 state |
| `ctx` | `RunContext`，携带数据库会话等运行时依赖，不进入 state，避免被序列化 |
| `END` | 终止标记 `__END__`。`set_finish_point(x)` 等价于 `add_edge(x, END)`，即 x 执行完即结束 |
| `max_steps` | 死循环保护，默认 40，各工作流编译时设 30 |
| `_trace` | 引擎自动追加每个节点的执行记录（名称、职责、耗时、异常栈） |

`_trace` 直接用于界面"Agent 执行过程"折叠面板与《测试报告》，不需要额外埋点。

### 2.3 异常处理

节点抛异常时，引擎记录 `status: error` 与裁剪后的 traceback，写入 trace 后继续向上抛出。上层 `workflows.run()` 记录到 `agent_run` 表并返回 500。单节点失败不会静默吞掉。

## 3. 八条工作流

### 3.1 知识问答 `qa`

| 节点 | 职责 |
| --- | --- |
| `analyze` | 识别问题类型（时间节点/材料要求/奖项设置/报名条件/经费政策），产出检索语句 |
| `retrieve` | 知识库混合检索，取 top_k |
| `answer` | 拼接上下文 + Prompt，模型生成带引用的回答 |
| `no_hit` | 未命中时的说明与改进建议 |

条件路由（`_qa_grade`）：

```
hits 为空                    → no_hit
max_score < MIN_SCORE(0.12)  → no_hit（"弱命中"也按未命中处理）
其余                         → answer
```

`answer` 节点内部再判一次：模型可用则走 LLM，否则走 `compose.extractive_answer()` 做原文抽取。两条路径都返回 citations。

阈值 `RETRIEVE_MIN_SCORE` 是可调的核心参数。设太低会拿不相关片段硬答，设太高会频繁拒答。当前 0.12 是基于样例知识库调出的经验值，接入真实文档后建议用「检索测试」重新校准。

### 3.2 竞赛推荐 `recommend`

| 节点 | 职责 |
| --- | --- |
| `profile` | 读取学生画像与参赛历史（工具 `student_profile`） |
| `candidates` | 规则引擎打分排序（工具 `recommend_candidates`） |
| `rerank_llm` | 模型在候选内重排，产出分层与理由 |
| `rerank_rule` | 无模型时按分数分层 |
| `format` | 组织推荐结论 |

路由：`llm.available 且有候选` → `rerank_llm`，否则 → `rerank_rule`。

**打分规则**（`tools.recommend_candidates`，基线 30 分）：

| 条件 | 分值 |
| --- | --- |
| 专业在赛事适配列表内 | +25 |
| 专业不在列表内 | −18 |
| 年级在赛事适龄范围 | +12 |
| 年级不符 | −20 |
| 技术方向关键词命中（每命中 1 个 +6，最多 +12） | +6~12 |
| 已参加过该赛事 | −8 |
| 报名截止 ≤14 天 | +8 |
| 报名截止 15-30 天 | +6 |
| 报名截止 31-60 天 | +3 |
| 报名已截止 | −25 |
| 本年通知未发布 | −5 |
| 难度 ≥5 且学生为大一大二 | −12 |
| 往年获奖率（连续计入，0-8 分） | `min(8, 获奖率 × 16)` |

分数裁剪到 0-100，理论满分为 95。分层：难度 ≥4 为「冲刺」，分数 ≥60 为「稳妥」，其余「保底」。

**为什么基线是 30 而不是 50**：基线和加分项加起来必须留出余量。
基线取 50 时，"专业对口 + 年级合适 + 临近截止"三项就把分数顶到 95-100，
一批赛事并列同分，列表看起来排了序其实没有区分度。
基线降到 30、获奖率改为连续计分后，同一学生的候选分差自然拉开到 77-86 区间。
这是一处实测发现的调整，记录在《测试报告》D-17。

这套规则的意义是**可解释**。评审问"为什么推荐这个"时，能逐项对应到具体条件，而不是"模型觉得合适"。

### 3.3 备赛辅助 `prep`

| 节点 | 职责 |
| --- | --- |
| `resolve` | 定位赛事：从 team_id 或赛事名解析出赛事+届次+规则 |
| `retrieve` | 四路检索：报名条件/提交材料/时间安排/评审标准，取并集去重 |
| `plan` | 倒排计划。模型可用走 Prompt，否则走 `_rule_plan` |
| `format` | 组织输出，附引用 |

`_rule_plan` 的倒排比例：选题组队 15%、方案设计 25%、开发实验 35%、材料撰写 15%、提交答辩 10%。总天数取"今天到比赛开始（或报名截止）"的天数，最少 3 天。

### 3.4 材料评审 `review`

| 节点 | 职责 |
| --- | --- |
| `extract` | 抽取材料正文（支持直接传入 content 或 file_path），截断到 12000 字 |
| `retrieve` | 检索评审标准（申报书规范、评分细则） |
| `review` | 分维度检查。有模型走 Prompt 输出结构化 JSON，否则走 `_rule_review` |
| `format` | 生成评审报告 |

`_rule_review` 是启发式检查，四类信号：

1. **结构完整性**：查「创新点 / 技术路线 / 可行性 / 预期成果 / 进度 / 团队」六个关键词，缺失项逐条报出并给补写建议。
2. **篇幅**：<800 字判高风险，<1500 字扣分。
3. **空话检测**：命中「具有重要意义 / 积极探索 / 不断完善 / 大大提升 / 有效推动」等词则提示替换为可量化表述。
4. **数据密度**：统计 `数字+单位` 模式出现次数，<3 处提示补充。

答辩问题为固定题库（8 条），围绕技术原创性、降级方案、最难技术点、分工、指标依据、周期缓冲、数据合规、现场演示。有模型时由模型针对材料薄弱点生成。

### 3.5 预算申请 `budget`

| 节点 | 职责 |
| --- | --- |
| `parse` | 解析入参，关联 team_id 时自动补全赛事名、级别、队伍名；缺省人数 3、天数 3 |
| `compute` | 按 `system_config.budget_rules` 测算明细 |
| `check` | 检索管理办法片段，有模型则做合规比对 |
| `format` | 输出明细表、校验提示、预算说明 |

测算逻辑（`services/budget.compute_budget`）：

- 地点判定：本地 / 省内 / 省外，决定交通、住宿、伙食的单位标准
- 报名费上限 1500 元/队，超出自理
- 住宿按 `人数 × (天数-1)` 晚计
- 伙食补助按 `人数 × 天数` 计
- 材料费单队默认 600 元，上限 1000
- 保险 30 元/人
- 支持 `extras` 追加自定义科目

校验项：单队总额上限 12000 元、材料费占比上限 25%、数量单价为 0 的异常行。

### 3.6 借款辅助 `loan`

| 节点 | 职责 |
| --- | --- |
| `build` | 依据批复预算或手工金额生成借款单要素 |
| `format` | 输出要素与提示 |

含金额大写转换（`money_to_chinese`，已验证 11 个用例）、用途自动表述、应附单据清单。校验：金额为 0 报高风险；关联预算状态非"已批准/已提交"给中风险提示。

### 3.7 报销辅助 `reimburse`

| 节点 | 职责 |
| --- | --- |
| `check` | 票据要素校验 + 预算符合性 + 制度比对（有模型时） |
| `format` | 输出结论与问题清单 |

校验规则：

| 检查项 | 级别 |
| --- | --- |
| 金额为空或 0 | 高 |
| 缺发票号 | 高 |
| 缺开票日期 | 中 |
| 餐饮类支出列在非伙食科目 | 中 |
| 总额超批复预算 | 高（列出超支金额） |
| 缺必备附件 | 由 `required_attachments` 比对 |

结论逻辑：无高风险问题且附件齐全 → "可提交报销"；否则列出高风险项数与缺失附件数。

### 3.8 数据统计 `stats`

| 节点 | 职责 |
| --- | --- |
| `parse` | 自然语言转查询条件。有模型走 Prompt 输出 JSON，否则正则抽年份/级别/奖项/维度 |
| `aggregate` | 数据库聚合 + 明细 |
| `format` | 输出统计结论 |

规则解析兜底能力：识别 `20\d{2}` 年份、"国家级/省级/校级"、"特等奖…优秀奖"、是否"获奖"过滤，以及分组维度关键词（年/赛事/级别/专业/教师/获奖等级）。

**统计口径**（写死在 SQL 里，不由模型决定）：

- 参赛项目数 = `team` 表记录数
- 获奖数 = `award_level != '无'` 的记录数
- 获奖率 = 获奖数 / 参赛项目数
- 专业维度按项目**负责人**专业归集，避免多成员重复计数

## 5. Prompt 全文

提示词集中在 `backend/agent/prompts.py`。下面逐条说明设计意图。

### 5.1 SYSTEM_QA（知识问答系统提示）

```
你是高校学科竞赛辅助服务智能体的问答模块，服务对象是学生、指导教师和竞赛管理人员。

严格遵守以下规则：
1. 只依据【资料片段】回答，不得使用片段之外的事实。片段中没有的内容，直接说明"知识库中未收录"，不要推测。
2. 每个结论句后用 [编号] 标注来源，例如 [1]、[2][3]。
3. 涉及时间节点、金额、名额、奖项等级、材料清单等硬性信息时，必须逐字忠实于原文，不得改写数字和期限。
4. 如果片段之间存在冲突，指出冲突并说明各自的出处。
5. 回答使用简洁的中文，先给结论，再给依据细节。不要重复问题本身。
6. 不要编造文件名、条款号或链接。

输出格式（纯文本，不要 Markdown 代码块）：
结论：一到两句话回答核心问题。
依据：
- 要点 [编号]
- 要点 [编号]
补充：仅在确有需要提醒的事项时输出，否则省略。
```

设计意图：

- 第 1、3 条是对抗幻觉的核心。第 3 条单列，因为竞赛场景里"错一天就等于没用"。
- 第 4 条用于处理多份文件口径不一致的真实情况（比如旧版办法和新版细则冲突），让系统暴露矛盾而不是悄悄选一个。
- 第 6 条针对模型爱编造条款号的问题。
- 固定输出结构是为了前端能稳定渲染，也让评审一眼看出"哪句有出处"。

### 5.2 QA_USER（用户消息模板）

```
【资料片段】
{context}

【用户问题】
{question}

请依据上述片段回答。
```

`context` 由 `compose.hits_to_context` 生成，每段格式为 `[n] 来源：文档名 第x页 · 章节` + 正文。

### 5.3 NO_HIT_ANSWER（未命中模板）

不使用模型，纯字符串模板：

```
知识库中暂未检索到与「{question}」直接相关的规定或数据。

可能的原因：
{reasons}

建议：
1. 换用更具体的说法，例如把"什么时候交材料"改为"XX 竞赛 参赛作品 提交截止时间"；
2. 在「知识库」页面确认相关文件已导入（目前共收录 {doc_count} 份文件）；
3. 若确属新增政策，请联系竞赛负责人补充入库后再查询。
```

设计意图：**答不出就说答不出，并给出可执行下一步**。这比让模型编一个答案更有价值，也是需求方最可能当场测试的点。

### 5.4 RECOMMEND_RERANK（竞赛推荐重排）

```
你是竞赛匹配专家。根据学生画像和候选竞赛清单，选出最合适的 5 项并排序。

学生画像：
{profile}

候选竞赛（含适配专业、年级、难度、往年数据）：
{candidates}

要求：
1. 优先考虑专业对口、年级符合、时间不与已参加项目冲突的赛事；
2. 结合往年获奖率，对"值得冲"和"稳一稳"做出区分；
3. 每条给出 2 句话理由，必须引用候选清单中的客观信息（适配专业、难度、往年获奖数），不得杜撰；
4. 输出严格 JSON，不要任何多余文字：

{"items": [{"code": "赛事代码", "name": "赛事名称", "reason": "理由", "tier": "冲刺/稳妥/保底", "prepare_weeks": 4}]}
```

关键在第 3 条：要求理由必须引用候选清单里的客观字段。实测这能显著减少"该赛事含金量高、有助于提升能力"这类废话。

输出 JSON 后由 `_rec_llm` 按 `code` 回填候选的完整数据，**模型只决定顺序、分层和措辞，不能修改分数**。

### 5.5 PREP_PLAN（备赛计划）

```
你是备赛规划助手。依据竞赛规程片段，为该参赛项目生成备赛计划。

【竞赛与队伍信息】
竞赛：{competition}
队伍：{team}
距离截止/比赛：{days} 天

【规程片段】
{context}

要求：
1. 时间计划必须落在给定天数内，倒推排布，给出阶段名、起止日期（YYYY-MM-DD）、关键产出；
2. 任务清单按"必须完成/建议完成"分组，每条注明责任角色（负责人/成员/指导教师）；
3. 材料准备建议逐项列出规程要求的材料，并标注容易出错的点；
4. 规程没写的不要编。若片段信息不足以排期，明确指出缺哪些信息。

输出 Markdown 格式，包含三部分：## 时间计划 / ## 任务清单 / ## 材料准备清单。
```

第 1 条给出明确的天数约束，避免模型排一个 90 天的计划而实际只剩 30 天。第 4 条允许模型说"信息不足"，比硬编更可信。

### 5.6 MATERIAL_REVIEW（材料评审）

```
你是竞赛申报材料评审专家，参照评审要点对提交材料做初评。

【竞赛要求（来自知识库）】
{requirements}

【待评审材料】
{content}

请从以下维度逐项检查，输出问题与修改建议：
1. 完整性：要求提交的内容是否齐全，缺什么；
2. 规范性：格式、字数、结构是否符合要求；
3. 内容质量：创新点是否清晰、技术路线是否可行、工作量与难度是否匹配；
4. 表达问题：空话套话、逻辑跳跃、数据缺失。

每条问题必须引用材料中的原句或指出"缺失"，并给出可直接替换的改写建议。不要泛泛评价。

输出严格 JSON：
{"score": 78, "dimensions": [{"name": "完整性", "score": 80, "comment": "..."}],
  "issues": [{"severity": "高/中/低", "location": "所在章节或原句", "problem": "...", "suggestion": "..."}],
  "defense_questions": ["答辩可能被问到的问题"]}

答辩问题给 8 条，要针对材料的具体薄弱点，不要通用套话。
```

"必须引用原句"和"不要泛泛评价"是这条 Prompt 的关键。没有这两句，模型会输出"建议进一步完善技术方案"这类无效建议。

### 5.7 BUDGET_EXPLAIN（预算合规）

```
你是高校竞赛经费预算助手。依据该校经费管理办法片段，对下列预算明细做合规性检查。

【管理办法片段】
{context}

【预算明细】
{items}

【预算总额】{total} 元

要求：
1. 逐项判断是否符合开支范围，指出超标或无依据的科目；
2. 检查是否有明显漏项（如报名费、保险、耗材）；
3. 给出申请书中"预算说明"一段可直接使用的文字（200 字以内），语气为正式行政公文；
4. 只依据片段中的标准判断，片段未涉及的科目标注"需向学院确认"，不要编造标准。

输出严格 JSON：
{"compliant": true, "issues": [{"item": "科目", "problem": "...", "advice": "..."}],
  "missing_items": ["建议补充的科目"], "statement": "预算说明正文"}
```

第 3 条是实用性设计：生成的文字能直接粘进申请书，省掉教师的重复劳动——这正是需求里"教师在经费材料填报过程中重复工作较多"的痛点。

第 4 条防止模型编造一个不存在的报销标准。

### 5.8 REIMBURSE_CHECK（报销审核）

```
你是竞赛经费报销审核助手，依据报销规定检查材料完整性。

【报销规定片段】
{context}

【报销单据】
{items}

【预算批复金额】{budget} 元，【实际支出】{total} 元

检查以下各项并输出结论：
1. 票据要素是否齐全（发票号、日期、金额、开票单位）；
2. 支出是否在批复预算范围内，超支多少；
3. 是否存在科目错配（如餐饮计入差旅）；
4. 缺少哪些附件（审批单、行程单、签到表等）。

输出严格 JSON：
{"pass": false, "total": 0, "over_budget": 0,
  "issues": [{"level": "高/中/低", "item": "...", "problem": "...", "fix": "..."}],
  "missing_attachments": ["..."], "conclusion": "一句话审核结论"}
```

注意：**总额、超支金额、是否通过这三个字段由规则计算，模型输出仅作为补充意见展示**（`r["llm_check"]`），不覆盖规则结论。这是防止模型算错数导致单据出错。

### 5.9 QUERY_PARSE（统计问数）

```
把用户的竞赛数据查询问题转换为结构化查询条件。

可用的字段与取值：
- year：年份整数，如 2024
- competition：赛事名称关键词
- level：赛事级别，取值 国家级 / 省级 / 校级 / 行业级
- award_grade：获奖级别，取值 国家级 / 省级 / 校级
- award_level：获奖等级，取值 特等奖 / 一等奖 / 二等奖 / 三等奖 / 优秀奖 / 无
- major：专业名称关键词
- teacher：指导教师姓名
- student：学生姓名
- group_by：分组维度，取值 year / competition / level / major / teacher / award_grade / award_level
- metric：指标，取值 count（参赛项目数）/ award_count（获奖数）/ award_rate（获奖率）/ amount（经费）

用户问题：{question}

只输出 JSON，不要解释：
{"year": null, "competition": null, "level": null, "award_grade": null, "award_level": null,
  "major": null, "teacher": null, "student": null, "group_by": "year", "metric": "count"}
```

**这是全系统唯一让模型"理解意图"的地方，但模型输出的只是查询条件，不是数据。** 条件会经过 `Filters` 白名单校验，非法值被忽略；越界的字段（比如试图注入 SQL）根本进不了查询构造，因为 `Filters` 只接受上述枚举字段。

`metric` 字段当前解析后不使用（统一返回 count/award_count/award_rate/amount 四项），保留是为了后续扩展。

## 6. 扩展指南

### 6.1 新增一条工作流

```python
# backend/agent/workflows.py
def build_xxx() -> StateGraph:
    g = StateGraph("新能力")
    g.add_node("step1", _fn1, "职责说明")
    g.add_node("step2", _fn2, "职责说明")
    g.set_entry_point("step1")
    g.add_edge("step1", "step2")
    g.set_finish_point("step2")
    return g

_BUILDERS["xxx"] = build_xxx          # 注册
WORKFLOW_LABELS["xxx"] = "新能力名称"  # 显示名
```

前端调用 `POST /api/agent/run {"workflow": "xxx", "payload": {...}}` 即可执行，无需改路由。

节点函数约定：`fn(state: dict, ctx: RunContext) -> dict`，返回要合并进 state 的字段。要新增事实数据，返回 `{"your_key": ...}`；要输出最终回答，返回 `{"answer": "...", "data": {...}, "citations": [...]}`。

### 6.2 迁移到官方 LangGraph

节点函数签名是 `fn(state, ctx)`，LangGraph 的是 `fn(state)`。迁移时需要把 `ctx` 通过以下任一方式带进去：

1. **闭包**：编译前用 `functools.partial` 绑定 db；
2. **state 传参**：把 `db` 放进 `state["_ctx"]`（不推荐，污染状态）；
3. **config 注入**：LangGraph 的 `config["configurable"]` 机制。

推荐第 1 种，改动最小：

```python
from functools import partial
from langgraph.graph import StateGraph, END

def make_graph(db):
    g = StateGraph(dict)
    g.add_node("retrieve", partial(_qa_retrieve, ctx=RunContext(db=db)))
    ...
```

同时需要把节点函数里的 `state.get(...)` 换成 LangGraph 的 reducer 写法（如果用 TypedDict 状态）。

`_trace` 机制需要自行补：LangGraph 有 `astream` 事件流，可在回调里收集。

### 6.3 调整推荐权重

当前权重硬编码在 `tools.recommend_candidates` 的加分段。若要完全可配，改为读取 `system_config` 中 `recommend_weights`（已预置该记录）：

```python
weights = db.query(SystemConfig).filter_by(key="recommend_weights").first().value
score += weights["major"] if matched else weights["major_miss"]
```

### 6.4 新增工具

```python
@tool("my_tool", "一句话说明用途", {"arg1": "说明"})
def my_tool(ctx: RunContext, arg1: str) -> dict:
    db = ctx.db
    return {"result": ...}
```

工作流里 `call_tool("my_tool", ctx, arg1="x")` 调用。工具返回必须是 JSON 可序列化的 dict（要写入 `agent_run` 表）。

## 7. 关键设计取舍

| 决策 | 取舍理由 |
| --- | --- |
| 自研 StateGraph 而非直接依赖 LangGraph | 减少一个较重依赖，便于在内网/离线环境部署；接口保持对齐，迁移成本可控 |
| 检索不用向量数据库 | 知识库规模在千级片段，纯 Python 内存索引毫秒级响应；少一个外部服务就少一个部署故障点 |
| 本地哈希向量 + BM25 混合 | 无 API Key 也能有可用的检索效果；接 API embedding 只需改一个配置项 |
| 无模型时降级而非报错 | 演示环境不一定有 Key；降级路径也能体现系统能力边界，反而便于讲解 |
| 统计全部走 SQL | 需求明确要求"以结构化业务数据为准"，也让数字可复核 |
| 规则校验与模型意见分离 | 报销、预算这类涉及钱的场景，模型结论只能作为参考，不能覆盖规则 |
